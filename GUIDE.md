## 1. Что это за сервис и зачем он нужен

Представьте почтовое отделение.

- **Клиент сайта** заполняет форму «Перезвоните мне» → это письмо.
- **Сервис** — это само отделение: принимает письмо, штампует (сохраняет в базу), кладёт в журнал (events.log).
- **Менеджер** — получатель: открывает базу и видит все заявки.

Этот сервис — «секретарь», у которого одна задача: **принять заявку, сохранить её в базу данных и зафиксировать, что она пришла**. Он не делает сайт, не заменяет Telegram-бота. Он — отдельная программа, к которой сайт и бот обращаются за тем, чтобы записать заявку.

### Почему отдельная программа, а не «всё в одном»?

Потому что так надёжнее. Если сайт упадёт — заявки, уже сохранённые в базе, не пропадут. Если бот зависнет — сервис продолжит принимать заявки от сайта. Каждый компонент занимается своим делом.

### Файл `app/__init__.py`

**Что это:** Пустой файл.

**Зачем нужен:** В Python пустой файл `__init__.py` в папке говорит интерпретатору: «эту папку можно импортировать как модуль». Благодаря ему в `main.py` можно написать `from app import db` — и Python поймёт, что `db` — это файл `app/db.py`.

**Менять ли:** Нет. Никогда.

---

### Файл `app/logging_config.py`

**Что это:** Настройка журнала (логирования). Лог — это текстовый дневник программы: что и когда произошло.

**Что делает построчно:**

```python
import logging
import sys

LOGGER_NAME = "lead_service"
```
- `LOGGER_NAME` — имя нашего журнала. Представьте, что у журнала есть табличка с названием. Все записи в этом журнале будут помечены именем `lead_service`.

**Функция `setup_logging()`**

Вызывается один раз при старте программы. Делает две вещи:
1. Создаёт обработчик для вывода в консоль (`StreamHandler(sys.stdout)`) — чтобы вы видели логи прямо в терминале.
2. Создаёт обработчик для вывода в файл `app.log` (`FileHandler("app.log")`) — чтобы логи сохранялись на диск.

Проверка `if logger.handlers: return logger` — защита: если настройка уже была сделана, не повторяем её. Иначе при перезагрузке логи дублировались бы.

**Функция `get_logger()`**

Возвращает журнал по имени. Вызывается из других файлов, когда нужно записать сообщение.

**Менять ли:** Только если хотите изменить формат записей (например, добавить номер строки) или место хранения файла `app.log`. В остальном — нет.

### Файл `app/db.py`

**Что это:** Вся работа с базой данных SQLite. База данных — это файл `leads.db` (создаётся автоматически при первом запуске).

**Что есть внутри:**

```python
DB_PATH = "leads.db"
```
Переменная с путём к файлу базы данных. Если захотите хранить базу в другом месте — поменять здесь.

**Функция `init_db()`**

«Инициализация базы». Вызывается при старте сервера (из `main.py`). Делает одно: выполняет команду SQL `CREATE TABLE IF NOT EXISTS leads (...)`.

- `CREATE TABLE IF NOT EXISTS` означает «создай таблицу, если её ещё нет». Если база уже существует — ничего не происходит, данные не стираются.

**Таблица `leads`** устроена так:

| Поле | Тип | Обязательное? | Что хранит |
|------|-----|---------------|------------|
| `id` | INTEGER | да (авто) | Номер заявки, растёт сам: 1, 2, 3... |
| `created_at` | TEXT | да | Дата и время создания (в UTC) |
| `name` | TEXT | нет | Имя клиента |
| `contact` | TEXT | да | Телефон, email или ник |
| `source` | TEXT | нет | Откуда пришла заявка (landing, telegram...) |
| `comment` | TEXT | нет | Комментарий клиента |

**Функция `get_connection()`**

«Дать соединение с базой». Это контекстный менеджер (через `with`). Работает как открытая дверь:
- открывает соединение с базой,
- отдаёт его тому, кто вызвал функцию,
- после использования — автоматически закрывает.

Параметр `check_same_thread=False` разрешает обращаться к базе из разных потоков. FastAPI (через uvicorn) обрабатывает запросы в нескольких потоках, поэтому это нужно. Без этого параметра была бы ошибка.

**Функция `save_lead(name, contact, source, comment)`**

«Сохранить заявку». Делает следующее:
1. Берёт текущее время в UTC (`datetime.now(timezone.utc).isoformat()`).
2. Открывает соединение с базой.
3. Выполняет SQL-команду `INSERT INTO leads (...) VALUES (...)`.
4. Делает `commit()` — фиксирует изменения (без этого данные не сохранятся).
5. Возвращает `id` новой заявки (`cursor.lastrowid`).

Параметры идут с типами:
- `name: str | None` — имя — строка или `None` (пусто).
- `contact: str` — контакт — обязательно строка (не может быть `None`).
- `source: str | None`, `comment: str | None` — необязательные.

**Менять ли:** Менять только если нужно добавить новые поля в таблицу. Тогда:
1. Добавить поле в `CREATE TABLE`.
2. Добавить параметр в `save_lead`.
3. Добавить значение в `INSERT INTO`.

Внимание: если база уже существует с прежней структурой, `CREATE TABLE IF NOT EXISTS` не добавит новое поле. Нужно либо удалить `leads.db` (и потерять данные), либо выполнить команду `ALTER TABLE` вручную.

### Файл `app/events.py`

**Что это:** Фиксация события «заявка принята». В ТЗ это называется «Вариант A — Event Log».

```python
EVENTS_LOG_PATH = "events.log"
```
Путь к файлу событий. Менять можно, если хотите хранить в другом месте.

**Функция `log_lead_saved(lead_id)`**

Принимает `lead_id` — номер сохранённой заявки. Делает две записи:
1. В основной журнал приложения (`get_logger().info(...)`) — попадает в консоль и `app.log`.
2. В отдельный файл `events.log` — простая запись `New lead saved: 42`.

Почему два места? ТЗ требует отдельный файл событий. Но основной лог приложения (в `app.log`) тоже полезен: там видны ошибки, время и контекст. Файл `events.log` — это «простой список принятых заявок», который удобно показывать менеджеру.

**Менять ли:** Если позже захотите отправлять email (Вариант B из ТЗ) — сюда добавится функция отправки письма. Логику в `events.log` можно оставить как есть.

### Файл `app/main.py`

**Что это:** Главный файл сервиса. Создаёт веб-сервер FastAPI и описывает endpoint (точку приёма заявок).

Это «лицо» сервиса — сюда приходят HTTP-запросы от сайта или бота.

#### Импорты (строки 1–16)

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field
```

- `FastAPI` — класс, создающий веб-приложение.
- `HTTPException` — генерирует HTTP-ошибки (например, 500).
- `RequestValidationError` — ошибка валидации входных данных.
- `BaseModel`, `Field` — инструменты Pydantic для описания структуры заявки.

```python
from app import db
from app.events import log_lead_saved
from app.logging_config import get_logger, setup_logging
```

Импорт своих модулей: базы, событий и логирования. Обратите внимание: `app.db` означает «файл `db.py` внутри папки `app`».

#### `logger = setup_logging()` (строка 18)

При импорте файла настраивается логирование. Дальше во всех функциях можно писать `logger.info(...)`, `logger.exception(...)`.

#### `lifespan()` (строки 21–26)

Специальная функция, которая запускается **при старте сервера** и **при остановке**.

```python
@asynccontextmanager
async def lifespan(_: FastAPI):
    db.init_db()                              # создаёт таблицу, если её нет
    logger.info("База данных инициализирована")
    yield                                     # здесь начинается работа сервера
    # (код после yield выполнился бы при остановке — сейчас его нет)
```

До `yield` — стартовая логика. После `yield` — логика завершения (у нас пусто).

#### Класс `LeadIn` (строки 29–40)

«Схема входной заявки». Описывает, какие поля принимает endpoint и какие правила для них действуют.

```python
class LeadIn(BaseModel):
    name: str | None = Field(default=None, description="Имя клиента")
    contact: str = Field(min_length=1, description="...")
    source: str | None = Field(default=None, description="...")
    comment: str | None = Field(default=None, description="...")
```

- `name: str | None = None` — имя — строка или `None`, по умолчанию `None`.
- `contact: str = Field(min_length=1)` — контакт — обязательная строка, минимум 1 символ. Если поле отсутствует или пустое — Pydantic вернёт ошибку валидации.
- `description=...` — текст, который показывается в Swagger UI на `/docs`.

Когда приходит JSON, FastAPI **автоматически** проверяет его по этой схеме. Если что-то не так — генерируется `RequestValidationError`, а мы её перехватываем (см. ниже).

#### Класс `LeadOut` (строки 43–48)

«Схема ответа». Описывает, что сервис вернёт при успехе.

```python
class LeadOut(BaseModel):
    id: int
    status: str = "ok"
    message: str = "Заявка принята"
```

- `id` — номер сохранённой заявки.
- `status` и `message` — с человекочитаемым описанием.

#### `tags_metadata` и `app = FastAPI(...)` (строки 51–78)

Создаётся объект приложения с настройками:
- `title` — заголовок в документации Swagger.
- `summary`, `description` — описание сервиса.
- `openapi_tags` — разделы (теги) для группировки endpoints в документации.
- `lifespan` — функция старта/остановки (см. выше).

#### Обработчик ошибок валидации (строки 81–87)

```python
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(_: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=400,
        content={"detail": "Невалидные данные заявки", "errors": exc.errors()},
    )
```

По умолчанию FastAPI при ошибке валидации возвращает код **422**. ТЗ требует **400**. Этот обработчик перехватывает ошибку и возвращает 400 с понятным текстом. `exc.errors()` — список конкретных проблем (какое поле, что не так).

#### Endpoint `GET /health` (строки 90–98)

```python
@app.get("/health", tags=["Служебные"], ...)
def health() -> dict:
    return {"status": "ok"}
```

«Проверка живости». Возвращает `{"status": "ok"}`. Используется для мониторинга: внешняя система раз в минуту обращается сюда и убеждается, что сервис отвечает.

#### Endpoint `POST /lead` (строки 101–137)

Главный endpoint. Принимает заявку, сохраняет, фиксирует событие.

```python
@app.post("/lead", tags=["Заявки"], response_model=LeadOut, ...)
async def create_lead(lead: LeadIn) -> LeadOut:
```

- `@app.post("/lead")` — регистрирует функцию как обработчик POST-запросов по адресу `/lead`.
- `lead: LeadIn` — FastAPI автоматически разбирает JSON из тела запроса и проверяет по схеме `LeadIn`.
- `-> LeadOut` — тип ответа; FastAPI по нему генерирует документацию.

Внутри функции:

```python
    try:
        lead_id = db.save_lead(
            name=lead.name,
            contact=lead.contact,
            source=lead.source,
            comment=lead.comment,
        )
    except Exception as exc:
        logger.exception("Ошибка при сохранении заявки в БД")
        raise HTTPException(status_code=500, detail="Внутренняя ошибка сервера") from exc
```

1. Пытаемся сохранить заявку в базу через `db.save_lead(...)`.
2. Если что-то пошло не так (база недоступна, файл удалён, диск переполнен) — перехватываем `Exception`, записываем полную ошибку в лог (`logger.exception` пишет и сообщение, и stacktrace) и возвращаем HTTP 500.

```python
    try:
        log_lead_saved(lead_id)
    except Exception:
        logger.exception("Не удалось записать событие в events.log")
```

3. Записываем событие «заявка принята». Если файл `events.log` нельзя записать (нет прав, диск полный) — **заявка уже сохранена**, поэтому мы не роняем запрос, а просто записываем ошибку в лог. Это принципиально: основная операция (сохранение в базу) уже выполнена.

```python
    return LeadOut(id=lead_id)
```

4. Возвращаем успешный ответ с номером заявки.

**Менять ли:** Менять, если добавляете новые поля в заявку (тогда — в `LeadIn` и в вызове `save_lead`). Если добавляете новые endpoints — добавляйте сюда же.

## 3. Как проходит заявка от начала до конца (атомный уровень)

Разберём путь одной заявки от формы на сайте до записи в базе.

### Шаг 0. Сервер запущен

Когда вы запускаете `uvicorn app.main:app`, происходит следующее:
1. Python загружает `app/main.py`.
2. Вызывается `setup_logging()` — создаётся логгер, настраиваются обработчики.
3. Создаётся объект `app = FastAPI(...)`.
4. Uvicorn запускает сервер и вызывает `lifespan()`:
   - `db.init_db()` создаёт таблицу `leads` (если её нет).
   - В лог пишется «База данных инициализирована».
5. Сервер начинает слушать порт 8000 и ждать запросы.

### Шаг 1. Клиент заполняет форму на сайте

Пользователь вводит имя и телефон. Сайт отправляет HTTP POST-запрос на адрес сервиса:

```
POST http://127.0.0.1:8000/lead
Content-Type: application/json

{
  "name": "Ирина",
  "contact": "+79990000000",
  "source": "landing",
  "comment": "Хочу консультацию"
}
```

### Шаг 2. FastAPI принимает запрос

Uvicorn передаёт запрос в FastAPI. FastAPI:
1. Видит, что это POST-запрос на `/lead` → вызывает функцию `create_lead`.
2. Берёт тело запроса (JSON) и пытается разобрать его по схеме `LeadIn`.

### Шаг 3. Валидация

Pydantic (часть FastAPI) проверяет поля:
- `name` есть, это строка → ок.
- `contact` есть, это строка, длина ≥ 1 → ок.
- `source`, `comment` есть, строки → ок.

Если бы `contact` отсутствовал — Pydantic создал бы `RequestValidationError`. Сработал бы обработчик `validation_exception_handler`, и клиент получил бы HTTP 400.

### Шаг 4. Сохранение в базу

Функция `create_lead` вызывает `db.save_lead(...)`:
1. В `save_lead` вычисляется `created_at` — текущее время в UTC в формате ISO (например, `2026-07-24T10:15:30.123456+00:00`).
2. Открывается соединение с `leads.db` через `get_connection()`.
3. Выполняется `INSERT INTO leads (created_at, name, contact, source, comment) VALUES (...)`.
4. `commit()` фиксирует запись.
5. `cursor.lastrowid` возвращает номер новой строки (например, 1).
6. Соединение закрывается.
7. `lead_id = 1` возвращается в `create_lead`.

Если бы база была недоступна — `save_lead` выбросил бы исключение, `create_lead` его перехватил бы, записал бы ошибку в лог и вернул бы HTTP 500.

### Шаг 5. Фиксация события

`create_lead` вызывает `log_lead_saved(lead_id=1)`:
1. В логгер `lead_service` пишется `INFO New lead saved: 1` → попадает в консоль и в `app.log`.
2. В файл `events.log` дописывается строка `New lead saved: 1`.

Если запись в `events.log` невозможна — ошибка логируется, но заявка уже сохранена в базе, поэтому клиент всё равно получает успешный ответ.

### Шаг 6. Ответ клиенту

`create_lead` возвращает `LeadOut(id=1)`. FastAPI превращает это в JSON:
```json
{"id": 1, "status": "ok", "message": "Заявка принята"}
```
Сайт получает ответ с кодом 200 и показывает пользователю «Спасибо, мы свяжемся с вами».

### Шаг 7. Менеджер смотрит базу

Менеджер открывает базу `leads.db` (например, через команду в README или через программу DB Browser for SQLite) и видит:
```
id | created_at                   | name  | contact      | source  | comment
1  | 2026-07-24T10:15:30+00:00   | Ирина | +79990000000 | landing | Хочу консультацию
```

## 4. Как масштабировать сервис

### Добавить новое поле (например, «тема обращения»)

1. В `app/db.py` → в `CREATE TABLE` добавить колонку, например `topic TEXT`.
2. В `app/db.py` → в `save_lead` добавить параметр `topic` и его в `INSERT INTO`.
3. В `app/main.py` → в класс `LeadIn` добавить поле `topic: str | None = None`.
4. В `app/main.py` → в вызове `db.save_lead(...)` передать `topic=lead.topic`.
5. Удалить старую базу `leads.db` (или выполнить `ALTER TABLE leads ADD COLUMN topic TEXT` вручную).
6. В `tests/test_lead.py` → обновить тесты, если нужно.

### Добавить новый endpoint (например, «получить список заявок»)

1. В `app/db.py` добавить функцию `get_all_leads()`, которая делает `SELECT * FROM leads`.
2. В `app/main.py` добавить:
```python
@app.get("/leads", tags=["Заявки"], summary="Список заявок")
def list_leads():
    return db.get_all_leads()
```

### Заменить Event Log на Email (Вариант B)

В `app/events.py` добавить функцию `send_email(lead_id, ...)`, которая через `smtplib` отправляет письмо. Вызывать её в `log_lead_saved` вместо (или вместе с) записью в `events.log`.

### Перевести на PostgreSQL

1. Установить драйвер (`psycopg2-binary`).
2. В `app/db.py` заменить `sqlite3` на `psycopg2`, изменить `get_connection()` и `save_lead()`.
3. Остальной код (`main.py`, `events.py`, `logging_config.py`) менять не нужно — они не знают, какая под ней база.

## 5. Сценарий 1: подключение к форме на сайте

У клиента есть сайт с формой «Перезвоните мне». Сейчас заявки приходят на email менеджеру и теряются. Нужно, чтобы они сохранялись в базу.

### Что нужно сделать

#### Шаг 1. Развернуть сервис на сервере клиента

1. Залить код сервиса на сервер (через git или архивом).
2. Создать виртуальное окружение: `python -m venv .venv`.
3. Активировать: `.venv\Scripts\activate` (Windows) или `source .venv/bin/activate` (Linux).
4. Установить зависимости: `pip install -r requirements.txt`.
5. Запустить: `uvicorn app.main:app --host 0.0.0.0 --port 8000`.

`--host 0.0.0.0` означает «слушать все сетевые интерфейсы», то есть принимать запросы не только с этого сервера, но и из сети. `127.0.0.1` слушал бы только локально.

#### Шаг 2. Изменить код формы на сайте

Найти в коде сайта обработчик формы (на PHP, JavaScript, Python — смотря на чём сайт). Сейчас он, вероятно, отправляет email. Нужно добавить (или заменить) отправку HTTP-запроса к сервису.

Пример на JavaScript (для формы в браузере):

```javascript
document.querySelector('form').addEventListener('submit', async (e) => {
  e.preventDefault();
  const data = {
    name: document.querySelector('#name').value,
    contact: document.querySelector('#phone').value,
    source: 'landing',
    comment: document.querySelector('#message').value
  };
  const response = await fetch('http://IP_СЕРВЕРА:8000/lead', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data)
  });
  if (response.ok) {
    alert('Спасибо! Мы свяжемся с вами.');
  }
});
```

Пример на PHP (на сервере):

```php
$data = json_encode([
    'name' => $_POST['name'],
    'contact' => $_POST['phone'],
    'source' => 'landing',
    'comment' => $_POST['message']
]);

$ch = curl_init('http://IP_СЕРВЕРА:8000/lead');
curl_setopt($ch, CURLOPT_POST, true);
curl_setopt($ch, CURLOPT_POSTFIELDS, $data);
curl_setopt($ch, CURLOPT_HTTPHEADER, ['Content-Type: application/json']);
curl_exec($ch);
curl_close($ch);
```

#### Шаг 3. Проверить связь

1. Открыть `http://IP_СЕРВЕРА:8000/docs` — должна открыться документация.
2. Отправить тестовую заявку через форму на сайте.
3. Проверить, что в `events.log` появилась запись `New lead saved: 1`.
4. Открыть базу `leads.db` и убедиться, что заявка там.

#### Что менять в коде сервиса

**Ничего.** Сервис уже готов принимать заявки с любым `source`. Сайт отправляет `source: 'landing'` — это просто строка, сервис её сохраняет как есть.

### Важное замечание про CORS

Если форма отправляет запрос **из браузера** напрямую к сервису (а сервис на другом домене/порту), браузер может заблокировать запрос из-за политики CORS. Тогда в `app/main.py` нужно добавить:

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://сайт-клиента.ru"],  # адрес сайта клиента
    allow_methods=["POST"],
    allow_headers=["*"],
)
```

Если же запрос отправляется с сервера сайта (PHP, Python) — CORS не нужен, потому что CORS — это ограничение браузера, а не сервера.

## 6. Сценарий 2: подключение к Telegram-боту

У клиента есть Telegram-бот, через который пользователи оставляют заявки. Сейчас они приходят в чат менеджеру и теряются. Нужно, чтобы они сохранялись в базу.

### Что нужно сделать

#### Шаг 1. Развернуть сервис на сервере

Так же, как в сценарии 1: залить код, установить зависимости, запустить `uvicorn`.

#### Шаг 2. Добавить в код бота отправку заявки в сервис

Telegram-бот — это отдельная программа (обычно на Python с библиотекой `aiogram` или `telebot`). Когда пользователь отправляет боту свои данные, бот должен дополнительно отправить HTTP-запрос к нашему сервису.

Пример на Python (с использованием библиотеки `requests`):

```python
import requests

def send_lead_to_service(name, contact, comment):
    url = "http://IP_СЕРВЕРА:8000/lead"
    payload = {
        "name": name,
        "contact": contact,
        "source": "telegram",
        "comment": comment
    }
    try:
        response = requests.post(url, json=payload, timeout=5)
        if response.ok:
            print("Заявка сохранена:", response.json())
        else:
            print("Ошибка сервиса:", response.status_code)
    except requests.RequestException as e:
        print("Сервис недоступен:", e)
```

Вызвать эту функцию в обработчике сообщения бота, когда пользователь отправляет контакт.

#### Шаг 3. Проверить связь

1. Написать боту в Telegram.
2. В терминале сервиса увидеть запись `New lead saved: 1` в `events.log`.
3. Открыть базу — заявка с `source: 'telegram'` должна быть там.

#### Что менять в коде сервиса

**Ничего.** Бот отправляет `source: 'telegram'` — сервис сохраняет как есть.

## 7. Что менять в коде, а что — нет

### Менять не нужно (сервис готов как есть)

- `app/main.py` — endpoint уже принимает заявку с любым `source`.
- `app/db.py` — таблица уже хранит `source`, так что сайт и бот различимы.
- `app/events.py` — фиксирует все события одинаково.
- `app/logging_config.py` — логирование универсально.
- `tests/` — тесты проверяют логику, а не источник заявки.

### Менять нужно (только на стороне клиента)

- **Сайт:** в коде формы — добавить отправку POST-запроса к сервису.
- **Бот:** в коде бота — добавить отправку POST-запроса к сервису.

### Менять опционально (если есть потребность)

| Что хочется | Где менять |
|-------------|-----------|
| Другой порт | В команде запуска `uvicorn ... --port 9000` |
| Хранить базу в другом месте | `app/db.py` → `DB_PATH` |
| Хранить events.log в другом месте | `app/events.py` → `EVENTS_LOG_PATH` |
| Добавить поле «тема» | См. раздел «Масштабирование» выше |
| Разрешить запросы из браузера (CORS) | `app/main.py` → `CORSMiddleware` |
| Отправлять email вместо log | `app/events.py` → добавить `send_email()` |

## Краткая схема для памяти

```
[Сайт / Telegram-бот]
        │
        │ POST http://IP:8000/lead  {name, contact, source, comment}
        ▼
[FastAPI (app/main.py)]
        │
        │ валидация (LeadIn)
        ▼
[db.save_lead()]
        │
        │ INSERT INTO leads
        ▼
[SQLite (leads.db)]   ────► [events.log]  «New lead saved: 1»
        │
        ▼
[Ответ 200 OK: {id, status, message}]
        │
        ▼
[Сайт/бот показывает «Спасибо»]
```

Вся логика сервиса — это этот путь. Поняв его, вы понимаете весь проект.
